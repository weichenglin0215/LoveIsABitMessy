## 一、這個系統在做什麼

### 1.1 起心動念

**這個專案的起點不是技術，是一個寫作上的困擾。**

我想寫短篇小說。但我發現自己一直在問同一個問題：怎麼讓我筆下的角色，不是「個性開朗的女孩」這種扁平的標籤，而是一個有血有肉、會自己呼吸的人？

我試著請 AI 幫我寫——但 AI 寫出來的角色，永遠像紙片人。原因不是 AI 不會寫，而是它不真的「理解」一個人。它寫得出「她皺起眉頭」，但寫不出「為什麼是這個人在這個瞬間皺起這個眉頭」。

要解決這件事，得從更底層的問題出發：**小說寫的是人，而好的故事，劇情必須由角色的個性自己推動，不是作者硬推**。如果舊情人 40 歲重逢於台北是一個故事框架，那麼「兩位都是台北土生土長的人」和「冷酷德國男 vs 委婉日本女」——同樣的框架會長出完全不同的兩本小說。

這個系統做的，就是為這件事而存在的工具集。

### 1.2 為什麼從愛情切入、為什麼分三階段

要讓 AI 理解人，得從人最複雜的部分下手。**愛情是人類情感裡最複雜的一塊，而且天然分成三個階段——曖昧、熱戀、失戀——每個階段都會把一個人不同的面向逼出來。**

一個在曖昧期主動外放、發限動、傳訊息不停的人，在熱戀期可能變得安穩內收，在失戀期又可能完全沉默——這種跨階段的差異，才是「人」真實的樣子。傳統的性格測驗給你一個固定標籤，但真實的人不會只有一種樣子。

LPAS（Love Personality Assessment System，愛情人格特質評量表）就是建立在這個觀察上的工具。

## 二、五個工具，一條動線

系統由五個前端工具組成，每一個都對應創作者真實工作流的一個步驟。

### Tool 1：LPAS 評量（`web/lpas_v3.html`）——產出角色的人格地基

填寫者作答 56 題（48 題情感題＋8 題性象限題，性象限可整段或單題跳過），系統會：
1. 從 4 個獨立行為軸（主動／被動、快／慢、外放／內斂、佔有／自由）計算出三個階段（曖昧、熱戀、失戀）各自的人格代碼
2. 把該代碼對應到 **16 個天候型之一**——海嘯、煙火、漩渦、陣雨、岩漿、太陽、藤蔓、燈塔、雷雨、流星、流沙、晨露、梅雨、晚霞、深海、迷霧
3. 性象限對應到 **4 個類型**：深情專一、鍾情博愛、靈肉分離、遊戲人間
4. 結果頁顯示三階段雷達圖、章節描述、配對提示，可下載角色卡 JSON、下載測驗紀錄、複製 Markdown

LPAS 完整規格另見 `LPAS愛情人格特質評量表企劃書_V3.md`。

**這一步的產出**：一張帶有人格骨架的角色卡，本機與雲端各存一份。

---

### Tool 2：角色卡編輯器（`web/characters_editor.html`）——補上血肉

LPAS 只給角色骨架，一個能上場的角色還需要：姓名、年齡、職業、外貌、習慣、口頭禪、生日、血型、與主角的關係、生圖 prompt⋯⋯。編輯器把這些欄位攤在介面上手動補完，並有兩個關鍵的 AI 輔助功能：

- **文字／圖片轉角色卡**：丟一段角色描述、或一張角色照片給 AI，自動生成完整角色卡
- **既有作品反推角色卡**：丟一篇你過去寫過的小說／文章，AI 會從中分析出角色的個性、口吻、習慣，反向產出角色卡——讓舊作裡的人物可以進到這個系統繼續被使用

V0.9.5.0 起新增「角色照片」區塊（拖曳上傳、自動縮圖為 256 與 1024 兩種尺寸）。

**這一步的產出**：一張完整可上場的角色卡，存入 Supabase `characters` 表。

---

### Tool 3：LoveLine 聊天（`web/loveline.html`）——驗證角色卡是否立得起來

這個工具是整套系統最關鍵、也最容易被低估的一個。

寫完角色卡之後，不直接拿去寫小說，而是先**讓不同的大模型扮演這個角色跟你聊天**。你在對話中觀察：這個 AI 用詞遣字、講話節奏、反應方式，是否符合角色的年齡、職業、個性？

- 一個 25 歲的咖啡店員工，會不會用 40 歲律師的詞彙？
- 一個被歸為「燈塔型」的內斂角色，會不會突然變得熱情外放？
- 同一張角色卡，丟給 Llama、Gemma、Mistral 等不同模型，哪個模型「接得最像」？

如果不對，你會回頭調整角色卡，再回來聊。聊到對為止。

**這一步的產出**：一張經過實戰驗證、AI 真的能穩定扮演的角色卡。

LoveLine 支援多使用者（每個使用者可設定自己的關聯角色與覆蓋設定）、自訂寫作風格、自訂模型參數、聊天記錄雲端同步。V0.9.5.0 起新增使用者備註欄、編輯彈窗改為兩欄版型。

---

### Tool 4：每日日記生成（`web/daily_run.html`）——讓角色活在時間裡

**日記不是日記，日記是縮微的小說。**

作者只需要寫每天 30~50 字的重點（等同條列式的小說粗綱），例如：

> 「今天主管在會議上當眾糾正我，我表面說好，回座位才發現手在抖。」

AI 會根據這份角色卡＋這段重點，自動發展成完整的日記文字，並由 ComfyUI 自動配上插圖。一個角色每天有日記，就是把角色從一張卡，變成一個正在過日子的人。

`daily_run.html` 是互動介面，可選演員、設定情境、即時看後台生成進度。V0.9.5.0 起新增「專案備註」欄（不送給 AI，只是作者自用）。

**這一步的產出**：每日一則完整日記＋插圖，存入 Supabase `diary_entries` 表，並編譯為靜態 HTML 頁。

---

### Tool 5：小說產生器（`web/novel_generator.html`）——組裝長篇

把所有東西組裝成一篇完整的小說。創作分成四個粒度，**每一層都可以作者介入修改，AI 根據該層產生下一層**：

```
粗綱（整個故事的梗概，可能只有一段）
  ↓ AI 展開
章（章節大綱，每章一段）
  ↓ AI 展開
節（每節細綱，每節數段）
  ↓ AI 展開
內文（實際小說文字）
```

而且這條路徑是雙向的：

- **正向**：作者寫粗綱 → AI 生章 → 作者調整章 → AI 生節 → 作者調整節 → AI 生內文
- **反向**：作者丟一本既有小說 → AI 分析出節→章→粗綱，方便研究、改編、或當作下一本的起點

關鍵設計：

- **演員 vs 角色名分離**（V0.9.5.0）：「角色卡」是演員，「角色名稱」是劇本中的角色名——例如角色卡「惠茹」演出劇本中的「寶蓮」，prompt 會自動用劇本角色名
- **作者備註**：彈窗大型 textarea，存進小說但不送給 AI
- **多本小說比對**功能
- **文字檔轉粗綱**：丟一段文字進去，AI 依起承轉合輸出條列式粗綱
- **文檔轉條列**（V0.9.4.0）：每個關鍵事件含「原劇情走向＋兩條 AI 替代戲劇化走向」

**這一步的產出**：完整章節結構的長篇小說，存入 Supabase。

## 三、五工具如何串成一條動線

```
┌─────────────────────────────────────────────────────────────┐
│                                                              │
│  LPAS ───► 編輯器 ───► LoveLine ───► 日記 ───► 小說產生器   │
│  人格骨架  補血肉     驗證          養活角色   組裝長篇      │
│                                                              │
│  ◄── 反向：既有小說 → 編輯器（反推角色卡）                  │

│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**作者每個步驟都可以介入。AI 是放大器，不是替代者。**

## 四、技術組成

### 4.1 整體架構

```
┌──────────────────┐
│  前端：純 HTML/  │  ← 五個 html 頁面（lpas_v3/characters_editor/
│  CSS/JS（無框架）│    loveline/daily_run/novel_generator）
└──────────────────┘
        ↕
┌──────────────────┐
│ 本機 Python 後端 │  ← debug_server.py（Port 8000/8081）
│                  │    管理任務異步、心跳、JSON 修復
└──────────────────┘
        ↕
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│  Ollama 大模型   │   │  ComfyUI 影像生成 │   │ Supabase 雲端 DB │
│ （gemma4 推薦）  │   │ （Z-image-turbo） │   │   PostgreSQL     │
└──────────────────┘   └──────────────────┘   └──────────────────┘
```

### 4.2 重點檔案

**前端：**

| `web/daily_run.html` | 每日日記中心 |

### 4.3 與舊版的不同

舊版開發手冊（`LoveIsABitMessy開發手冊_舊版.txt`）描述的是專案啟動期的最初架構：四個資料夾、四個 Python 檔、純本機。**這個架構早已被遠遠超越**：

| 項目 | 舊版（V0.1.x） | 現在（V0.9.5） |
|---|---|---|
| 前端 | 無，靜態 HTML 模板 | 五個互動式頁面 |
| 資料 | 純本機 JSON | 本機 + Supabase 雙寫 |
| 角色生成 | 手寫 JSON | LPAS 自動 + 編輯器補完 + 文字／圖片 AI 分析 |
| 角色驗證 | 無 | LoveLine 即時測試 |
| 小說生成 | 一篇就是一篇 | 粗綱→章→節→內文四階段，雙向 |
| 模型 | 單一 dolphin-mistral | 多模型可切換（gemma4 推薦） |

舊版手冊保留作為歷史紀錄，**實作上請以本文件為準**。

## 五、使用流程（精簡版，舊版手冊的更新）

### 5.1 一次性環境準備

1. 安裝 Ollama，下載 `gemma4`（或其他你想用的模型）
2. 安裝 ComfyUI，匯出 Z-image-turbo workflow 為 API 格式，存入 `comfy_workflows/`
3. 安裝 Python 3.10+ 與 `requests`、`jinja2` 套件
4. 設定 Supabase 連線（`web/js/supabaseClient.js`）

### 5.2 日常作業流程

**啟動：** 執行 `start_debug_server.bat`（會一併啟動 Ollama 與 ComfyUI）

**創建新角色：**
1. 開 `lpas_v3.html` 完成測驗 → 取得 LPAS 角色卡
2. 開 `characters_editor.html` 補完細節（或用 AI 從文字／圖片自動生成）
3. 開 `loveline.html` 跟新角色聊幾輪，調整角色卡到滿意
4. 角色完成，加入角色庫

**寫小說：**
1. 開 `novel_generator.html`，選擇演員（角色卡）並指派角色名稱
2. 寫粗綱 → AI 生章 → 修章 → AI 生節 → 修節 → AI 生內文 → 修內文
3. 也可以從既有小說反推回粗綱

**讓角色繼續活著：**
- 開 `daily_run.html`，每天為角色寫 30~50 字重點，AI 自動產出完整日記＋插圖

### 5.3 常見問題

| 問題 | 解法 |
|---|---|
| `debug_server.py` 無法讀取 Ollama 模型列表 | `pip install requests`，或設定 `OLLAMA_HOST` 環境變數 |
| `debug_server.py` 啟動時出現 `PermissionError: [WinError 10013] 存取權限不足` | 8081 埠被 Windows Hyper-V／WinNAT 保留範圍占走（不是被程式佔用，是核心層保留）。執行 `reserve_port_8081.bat`（會自動請求管理員權限）永久把 8081 從保留範圍中排除。內容為：`net stop winnat` → `netsh int ipv4 add excludedportrange protocol=tcp startport=8081 numberofports=1` → `net start winnat`。之後重開機也不會再被搶走。可用 `netsh int ipv4 show excludedportrange protocol=tcp` 檢查 8081 是否已在表中（後面有 `*` 表示 admin-managed）。 |
| 角色卡格式不一致（V1 / V3 混存） | 系統會自動透過 `lpas_v1_to_v3.js` 在載入時補上 V3 欄位 |
| 角色照片在編輯器看不到 | 確認 Supabase `characters` 表已新增 `photo_thumb` 與 `photo_full` 欄位 |
| LoveLine 載入雲端記錄時模型已被刪除 | LOG 欄會顯示原始字串，方便重新拉模型 |

## 六、開發規範摘要

完整規範見 `.agent/skills/SPEC.md`，重點：

- **檔案編碼**：一律 UTF-8
- **程式碼註解**：詳細的繁體中文註解
- **lpas.html 介面**：手機／PC 皆需滿畫面，套用 `screen_adaptive.js`、`lpas_styles.css`、px 單位、flexbox
- **其他網頁介面**：以 PC 為主，採用 `editer.css`、rem 單位、flexbox + grid
- **資料儲存**：本機與雲端各存一份
- **LOG 寫法**：參考 `daily_run.html` 的 textarea，只能添加，不能清空或覆蓋
- **禁止**：修改 HTML 模板基本結構、新增規範外的功能、修改 `screen_adaptive.js` 核心邏輯
